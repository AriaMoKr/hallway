# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

A WebXR hallway (three.js 0.186, plain ES modules, no bundler or build step): a corridor whose
doors lead to other web environments: vrlbry (https://ariamokr.github.io/vrlbry/, AriaMoKr/vrlbry,
whose conventions this project follows), Breadboard 8-bit's VR view
(https://ariamokr.github.io/breadboard/vr.html), music (https://ariamokr.github.io/music/,
AriaMoKr/music: a music room built from vrlbry, where Gutenberg's books on music play their scores) and Outside (https://ariamokr.github.io/outside/,
AriaMoKr/outside: a small garden built for the door link, whose `HALLWAY_DOOR` in
`public/js/way.js` is its entry here; keep them in step). All four take the VR hand-over.
`public/` is the whole site. `README.md` covers
using it, adding a door, and rendering the door views the site publishes. The door contract (what
a door's link tells the environment, how environments link back, the door views) is AriaMoKr/common's
README: the hallway takes its code from that package, pinned to a tag, with the doorway's portal,
the fade and the gamepad reading that the sites share.

Published at https://ariamokr.github.io/hallway/ from `main` of AriaMoKr/hallway by
`.github/workflows/pages.yml`.

## Commands

```bash
npm install      # postinstall: tools/vendor.mjs copies three, common, layersharedsession, Trystero (and IWER) into public/vendor/ (gitignored)
npm start        # tools/serve.mjs: public/ on http://localhost:8088/ (IPv6 only on Windows; for a Quest over adb reverse: npm start -- --host 127.0.0.1)
npm test         # node --test "test/*.test.js"
node tools/quest-check.mjs [--local] [--screenshot]   # on a Quest over adb: VR frame timing, the panel, Exit VR; report in perf/ (gitignored)
node tools/door-views.mjs [--port n] [--cdp <url>]    # the view out of every open door, rendered in a browser (a Quest over adb by default) from the dev server: public/views/<id>.jpg + views.json, and the link preview's public/social.jpg; rerun after changing the hall or its doors
```

## Layout

- `public/js/environments.js`: the doors' data. A door's `title` is its repository's name and its `subtitle` its page's `<meta name="description">` word for word; `textures.js`'s `plaqueTexture` fits all of it, the largest size from 26 px down, on even lines. Keep the `<noscript>` list in `index.html` in step (tested).
- `layout.js`: pure (no three, tested in Node). Hall dimensions (`HALL`), door slots, the plaque beside each open door (`PLAQUE`), `clampToHall` (walking), `doorCrossed` (the threshold that navigates), `castRay` (what a pointer hits: the hall is a box, so picking is plane math, no Raycaster over meshes), `entranceSpawn` and `doorSpawn` (where arrivals stand, spread by a key, a member id's `hash`, so a visitor always gets the same spot; tested inside the hall and apart).
- `arrival.js`: pure. Which door a visitor came back out of: `?from=<id>`, then Back (`back_forward` + the door in sessionStorage), then the referrer.
- `link.js`: pure. `doorPose`: how a visitor goes through a door, in the doorway's terms (`across`, `yaw`, `pitch`), which common's `doorLink` puts in the link as `dx`, `yaw`, `pitch`. The link itself (`doorLink`, `HALLWAY_ID`, `LINK_PARAMS`) comes from `common/door.js`, and the VR movement choice (`loadNav`, `saveNav`: localStorage `hallway.nav`) from `common/nav.js`: AriaMoKr/common (a GitHub dependency pinned to a tag, vendored and in the import map as `common/`), whose README is the contract and whose tests cover them. To take a newer one, move the tag in package.json and `npm install`.
- `together.js`: the shared session (README, "Together"). `Together` starts (`start`, a new room by default), leaves (`stop`), and steps out for a door and back (`pause`, `resume`) a session of the layer from AriaMoKr/layersharedsession (a GitHub dependency pinned to a tag; `session.js` is imported dynamically, so Trystero loads only with a session). The room is in the address (`?room=`, `replaceState`); main.js joins the one an arriving URL names. Per frame `update` sends the head and, in VR, the controllers (the layer's `readPose`), and the layer's avatars (`avatars.js`: `createAvatars`, then `place` for those in the hallway, page id `hallway`) draw the others from their interpolated poses, with no allocation; a wave from one (the layer's `channel('wave')`, as the test page's, at most once a second per visitor) bobs their head and lifts their name for 1.2 s (`avatars.wave`). `setName` cleans and keeps a name (`saveName`, `lss.*` storage shared by every site on the origin) and sends it (`session.setName`); `status` and `people()` say how it's going and who is where, worded by `presence.js` (pure: `placeName` maps a page id to "here", an environment's title or "elsewhere", also the layer's `pageName`; `statusText`; `peopleText`, the panel's string). The status follows the relays (`relays` events, a 10 s timer), `navigator.onLine` and failed handshakes in the layer's log. The overlay's Together section (name box, status, the others with round trips) and its Wave button show while in a session; the grip in VR waves too (`controls.onSqueeze`, with a haptic pulse). The app id (`APP_ID`) is the layer's test page's, so that page can watch a hallway room. To take a newer layer, move its tag in package.json and `npm install`.
- `hall.js` builds the scene from `builder.js` (world-space quads and boxes) with lighting baked into vertex colours by `bake.js`. Materials are unlit (`MeshBasicMaterial`); there are no real-time lights or shadows. A new light is an entry in hall.js's `lights` list.
- `common/portal.js` (AriaMoKr/common): the doorway shader, which `hall.js` hangs in every open doorway (`portalMaterial`, `openingGeometry`, `placePortal`, `setPicture` once a preview loads). It ray-casts a box behind the opening: the far wall is the preview picture, the floor, ceiling and sides are its edges stretched. The hallway sets `uTime` and `uGlow` each frame, and `door-view.js` stills them for a door view, as common documents.
- `door-view.js`: the view out of a door, for the environment behind it (common's README, "The view from your door"): `doorView` (pure: the eye on the threshold, the off-axis frustum onto the opposite wall's plane, the parameters an environment's portal hangs it with) and `renderDoorView` (into a render target, read back to a canvas, the fade hidden, the doorways still); `renderHallView`, the same from `HALL_VIEW`, is the link preview's picture (`public/social.jpg`, 1280 × 640: index.html's `og:image`, whose tags are tested against it). `__hallway.doorViews()` renders every open door's once the previews have loaded (`hall.previewsLoaded`), `__hallway.hallView()` the link preview's; `tools/door-views.mjs` reloads the page it finds (over DevTools: `Page.reload`) and writes them to `public/views/` and `public/social.jpg`. A new or changed door changes the views across the hall and the link preview: render them again and commit them.
- The end window (`hall.js`): its glass is `common/sky.js`'s `skyMaterial(skyTexture(), { yaw: 0 })`, outside's late afternoon at infinity (looking down the hall as one looks down the garden), drawn first and writing no depth; in front of it, `FIELDS.depth` out, hangs the hallway's own scenery, `textures.js`'s `fieldsTexture` (a flat picture of fields below the horizon, transparent above it, hazed in the sky's horizon colour, `skyColor`). The window's baked light is `skyColor` a little over the horizon.
- `textures.js`: every canvas texture (painted at start-up, seeded so they never change), but the sky, which is common's. `previewFallback` is a door's picture until its preview loads, or for good when it has none: its title fitted to the middle of the picture, which is all a doorway shows.
- The control panel: its place (between the entrance and the first door on its wall, clear of every door and plaque there: tested) and buttons are in `layout.js` (`PANEL`, `PANEL_BUTTONS`, `panelButtonAt`; `castRay` reports `kind: 'panel'` with `u`, `v`), its drawing in `panel.js` (redrawn only when its state or the button pointed at changes; its Together section shows the shared session: Start / Leave, its status, the invite link, and up to four others and where, then "+N more", from a string so it redraws only when they change: round trips stay off it; 0.7 m tall, hung clear of the chair rail at 1 m: tested), the VR navigation choices it sets (`move`, `turn`) kept by `common/nav.js` (localStorage `hallway.nav`). A new button is an entry in `PANEL_BUTTONS`, a label in `panel.js` and a case in `main.js`'s `controls.onPanel`.
- `common/gamepad.js` (AriaMoKr/common): pure and allocation-free. A gamepad as a first-person controller, read alike by the sites so a pad feels the same on both sides of a door: `readPad` (dead zone 0.18, linear; A uses, B and Back are both "back", the left stick clicked in hurries; an analogue button counts past half way), `firstPad` (the standard mapping first).
- `overlay.js`: the page around the view, in a `<main>` (index.html) with the canvas (`role="img"`, named in main.js): the doors list (a `<nav>`, each door a link, its name in `color.js`'s `readable` tint of its glow: 4.5:1 on the list plain and hovered, the backgrounds tested against style.css), the Together section, and Settings (a `<details>`): the control panel's Move and Turn as radio groups and Start / Leave shared session, which press the panel's buttons (`onNav`, `onSession` → `controls.onPanel`; `setPanel` from main.js's `showPanel`). The panel is only in 3D, so whatever it offers belongs in Settings too.
- `controls.js`: desktop, touch, gamepad and XR input into one rig (yaw) + camera (head). The gamepad, as in vrlbry, takes over when used (`padActive`, `onPadActive`: its hint, and the middle of the view is what it points at) and a mouse move or press hands back; it looks at vrlbry's speeds (2.4 and 1.6 rad/s) and is not polled in VR; in VR the left stick walks or aims a teleport (`move`), the right one snaps or turns smoothly (`turn`), and teleports go through `onTeleport` (main.js blinks the view). `main.js`: renderer, loop, going through doors (`go`: a fade, `common/fade.js`'s `Fade`, then `location.assign` of the door's link), arrival, VR entry including `sessiongranted`, fullscreen (the overlay's button, with webkit fallbacks; Esc, or a gamepad's B or Back, leaves it).

## Conventions

- Client URLs stay relative: the site may live under a path (`/hallway/`). Tested.
- Quest 3 is the performance target. Keep draw calls few (one mesh per material: merge static geometry into a `Builder`), allocate nothing per frame (reuse vectors and hit objects, index loops over `session.inputSources`), and keep lighting baked.
- Coordinates: metres, floor y = 0, entrance wall z = 0, hall along -z, left is -x; yaw 0 faces -z.
- Scripted testing: `window.__hallway` (renderer, scene, camera, rig, hall, layout, controls, overlay, fade, `go`, `enterVR`, `together`, `doorViews()`, `hallView()`, `tick(dt, n)`, `xrDevice`). A shared session needs two pages: open the same `?room=` in two tabs (each tab is its own visitor), `controls.onPanel('session')` presses Start / Leave, `overlay.myName` (set its value, dispatch `change`) renames, `overlay.wave.click()` waves (IWER: `xrDevice.controllers.right.updateButtonValue('squeeze', 1)`), and layersharedsession's test page in the same room lists everyone and logs who came, went, renamed and waved. Offline: define `navigator.onLine` as false and dispatch `offline`. A hidden browser pane gets no animation frames, so drive it with `tick()`. `?xr=emulate` installs IWER; aim its controllers with `xrDevice.controllers.right.position/quaternion`, `updateButtonValue('trigger', 1)`, `updateAxes('thumbstick', x, y)`. A gamepad: replace `navigator.getGamepads` with one returning a fake `{ connected: true, axes, buttons: [{ pressed }] }` and dispatch a `gamepadconnected` event. The browser pane never grants fullscreen: define `document.fullscreenElement` and dispatch `fullscreenchange` (real fullscreen was checked in Quest Browser, pressing the button over DevTools with `userGesture`).
- The embedded browser pane serves the dev server on port 8088 (`.claude/launch.json`). `hallway-quest` serves it on `127.0.0.1:8089` as well, for the tools that reach it from a Quest through `adb reverse` (`--port 8089`): Quest Browser cannot reach the IPv6-only one there (checked).
