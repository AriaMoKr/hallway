# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

A WebXR hallway (three.js 0.186, plain ES modules, no bundler or build step): a corridor whose
doors lead to other web environments: vrlbry (https://ariamokr.github.io/vrlbry/, AriaMoKr/vrlbry,
whose conventions this project follows), Breadboard 8-bit's VR view
(https://ariamokr.github.io/breadboard/vr.html), music (https://ariamokr.github.io/music/,
AriaMoKr/music: a music room built from vrlbry, where Gutenberg's books on music play their scores) and Outside (https://ariamokr.github.io/outside/,
AriaMoKr/outside: a small garden built for the door link, whose `HALLWAY_DOOR` in
`public/js/way.js` is its entry here; keep them in step), and two rooms made from
AriaMoKr/RoomTemplateEmpty and still empty, art (https://ariamokr.github.io/art/, AriaMoKr/art,
soon a gallery) and video (https://ariamokr.github.io/video/, AriaMoKr/video, soon a room to watch
videos in), each with its entry here as its `public/js/config.js`'s `hallwayDoor()`. All six take
the VR hand-over. On an Android TV the hallway runs in AriaMoKr/HallwayApp (the site in a
full-screen WebView whose user agent ends ` HallwayTV/<version>`; its README has the install, the
build and its release workflow), where the page is in TV mode (common's `tv.js`).
`public/` is the whole site. `README.md` covers
using it, adding a door, and rendering the door views the site publishes. The door contract (what
a door's link tells the environment, how environments link back, the door views) is AriaMoKr/common's
README: the hallway takes its code from that package, pinned to a tag, with the doorway's portal,
the fade, the gamepad reading, the TV app's remote and the walking controls that the sites share.

Published at https://ariamokr.github.io/hallway/ from `main` of AriaMoKr/hallway by
`.github/workflows/pages.yml`, which calls common's workflow at the same tag as package.json's
(`npm ci`, `npm test` on Node 24, tsc's check among it, then `public/`).

## Commands

```bash
npm install      # postinstall: common's vendor copy (node_modules/common/tools/vendor.mjs) copies what vendor.json lists, three, common, layersharedsession, Trystero (and IWER), into public/vendor/ (gitignored)
npm start        # tools/serve.mjs, common's dev server on port 8088: public/ on http://localhost:8088/ (IPv6 only on Windows; for a Quest over adb reverse: npm start -- --host 127.0.0.1)
npm test         # node --test "test/*.test.js", tsc's check of public/js/ among them (test/types.test.js)
npm run types    # tsc -p tsconfig.json alone
node tools/quest-check.mjs [--local] [--screenshot]   # on a Quest over adb: VR frame timing, the panel, Exit VR; report in perf/ (gitignored)
node tools/door-views.mjs [--port n] [--chrome]       # the view out of every open door, rendered in a browser (a Quest over adb by default; --chrome: a headless Chrome of its own, common's launchChrome, in this PC's fonts) from the dev server: public/views/<id>.jpg + views.json, and the link preview's public/social.jpg; rerun after changing the hall or its doors
```

## Layout

- `public/js/environments.js`: the doors' data. A door's `title` is its repository's name and its `subtitle` its page's `<meta name="description">` word for word; `textures.js`'s `plaqueTexture` fits all of it, the largest size from 26 px down, on even lines. Keep the `<noscript>` list in `index.html` in step (tested).
- `layout.js`: pure (no three, tested in Node). Hall dimensions (`HALL`), door slots, the plaque beside each open door (`PLAQUE`), `clampToHall` (walking), `doorCrossed` (the threshold that navigates), `castRay` (what a pointer hits: the hall is a box, so picking is plane math, no Raycaster over meshes; it writes every field of the hit it is given, which the controls reuse from ray to ray, and `walkable` is true on the floor alone: tested), `entranceSpawn` and `doorSpawn` (where arrivals stand, spread by a key, a member id's `hash`, so a visitor always gets the same spot; tested inside the hall and apart).
- `arrival.js`: pure. Which door a visitor came back out of: on Back or Forward (`back_forward`) the door the history entry was left by (main.js's `rememberDoor` writes it into `history.state`, `hallwayDoor`, beside the layer's fields), then `?from=<id>`, then on Back the door last gone through in the tab (sessionStorage), then the referrer.
- `link.js`: pure. `doorPose`: how a visitor goes through a door, in the doorway's terms (`across`, `yaw`, `pitch`), which common's `doorLink` puts in the link as `dx`, `yaw`, `pitch`. The link itself (`doorLink`, `HALLWAY_ID`, `LINK_PARAMS`) comes from `common/door.js`, and the VR movement choice (`loadNav`, `saveNav`: localStorage `hallway.nav`) from `common/nav.js`: AriaMoKr/common (a GitHub dependency pinned to a tag, vendored and in the import map as `common/`), whose README is the contract and whose tests cover them. To take a newer one, move the tag in package.json and `npm install`.
- `together.js`: the shared session (README, "Together"), run by the layer's controller from AriaMoKr/layersharedsession (a GitHub dependency pinned to a tag; its `together.js`, whose README has its API): `hallwayTogether` is `createTogether({ appId: APP_ID, page: 'hallway', camera, renderer, hands, avatars: { parent: scene, font: SANS }, pageName })`, and the rest of the file is the hallway's words for it, from `presence.js`. The controller starts (`start`, a new room by default), leaves (`stop`), and steps out for a door and back (`pause`, `resume`) a session (`session.js` is imported dynamically, so Trystero loads only with a session). The room is in the address (`?room=`, `replaceState`); main.js joins the one an arriving URL names. Per frame `update` sends the head and, in VR, the controllers, and the layer's avatars draw those on the hallway's page from their interpolated poses, with no allocation; a wave from one (`channel('wave')`, at most once a second per visitor) bobs their head and lifts their name for 1.2 s, unless `reduceMotion`. `setName` cleans, keeps (`lss.*` storage shared by every site on the origin) and sends a name. main.js listens: `on('change')` redraws the panel and the overlay, `on('notice')` toasts (`noticeToast`: `join`, `arrive`, which the controller tells from its own record of each peer's page, `leave`, `wave`). The words are `presence.js`'s (pure: `placeName` maps a page id to "here", an environment's title or "elsewhere", also the layer's `pageName`; `statusText` over the controller's `condition()` and `company()`, `sessionStatus`; `noticeText`; `peopleList`, the overlay's others, `sessionPeople`; `peopleText`, the panel's string, `panelPeople`). The status follows the relays, a 10 s wait for them, `navigator.onLine` and failed handshakes, all from `condition()`. `test/presence.test.js` runs the words over the layer's controller with a stand-in session. The overlay's Together section (name box, status, the others with round trips) and its Wave button show while in a session; the grip in VR waves too (`controls.onSqueeze`, with a haptic pulse). The app id (`APP_ID`) is the layer's test page's, so that page can watch a hallway room. To take a newer layer, move its tag in package.json and `npm install`.
- `hall.js` builds the scene from `builder.js` (world-space quads and boxes) with lighting baked into vertex colours by `bake.js`. Materials are unlit (`MeshBasicMaterial`); there are no real-time lights or shadows. A new light is an entry in hall.js's `lights` list.
- `common/portal.js` (AriaMoKr/common): the doorway shader, which `hall.js` hangs in every open doorway (`portalMaterial`, `openingGeometry`, `placePortal`, `setPicture` once a preview loads). It ray-casts a box behind the opening: the far wall is the preview picture, the floor, ceiling and sides are its edges stretched. The hallway sets `uTime` and `uGlow` each frame, and `door-view.js` stills them for a door view, as common documents.
- `door-view.js`: the view out of a door, for the environment behind it (common's README, "The view from your door"): `doorView` (pure: the eye on the threshold, the off-axis frustum onto the opposite wall's plane, the parameters an environment's portal hangs it with) and `renderDoorView` (into a render target, read back to a canvas, the fade hidden, the doorways still); `renderHallView`, the same from `HALL_VIEW`, is the link preview's picture (`public/social.jpg`, 1280 × 640: index.html's `og:image`, whose tags are tested against it). `__hallway.doorViews()` renders every open door's once the previews have loaded (`hall.previewsLoaded`), `__hallway.hallView()` the link preview's; `tools/door-views.mjs` reloads the page it finds (over DevTools: `Page.reload`) and writes them to `public/views/` and `public/social.jpg`. A new or changed door changes the views across the hall and the link preview: render them again and commit them.
- The end window (`hall.js`): its glass is `common/sky.js`'s `skyMaterial(skyTexture(), { yaw: 0 })`, outside's late afternoon at infinity (looking down the hall as one looks down the garden), drawn first and writing no depth; in front of it, `FIELDS.depth` out, hangs the hallway's own scenery, `textures.js`'s `fieldsTexture` (a flat picture of fields below the horizon, transparent above it, hazed in the sky's horizon colour, `skyColor`). The window's baked light is `skyColor` a little over the horizon.
- `textures.js`: every canvas texture (painted at start-up, seeded so they never change), but the sky, which is common's. `previewFallback` is a door's picture until its preview loads, or for good when it has none: its title fitted to the middle of the picture, which is all a doorway shows.
- The control panel: its place (between the entrance and the first door on its wall, clear of every door and plaque there: tested) and buttons are in `layout.js` (`PANEL`, `PANEL_BUTTONS`, `panelButtonAt`; `castRay` reports `kind: 'panel'` with `u`, `v`), its drawing in `panel.js` (rows for Move and Turn, then common's accessibility settings, Motion: System / Less / Full, Vignette and Seated: On / Off, every value one common keeps: tested; redrawn only when its state or the button pointed at changes; its Together section shows the shared session: Start / Leave, its status, the invite link, and up to four others and where, then "+N more", from a string so it redraws only when they change: round trips stay off it; 0.86 m tall, 512 × 784, hung clear of the chair rail at 1 m with its top in reach: tested, so a new row means tightening the others), the VR navigation choices it sets (`move`, `turn`) kept by `common/nav.js` (localStorage `hallway.nav`). A new button is an entry in `PANEL_BUTTONS`, a label in `panel.js` and a case in `main.js`'s `controls.onPanel`. `large` (`buildHall`'s, a TV's) makes its text a fifth larger, each line fitted to its place (`fitText`).
- TV mode is `common/tv.js` (AriaMoKr/common's README, "The TV app", whose checklist every site behind the doors follows), when `tvMode()` (the app's user agent, `isTV`, or `?tv=emulate`): `html.tv` (style.css: the 10-foot view, 18 px text, a 4 px focus ring on a dark halo: tested), no Enter VR or Fullscreen, and the remote (main.js's `remote`, common's `Remote`, a capturing `keydown` before the controls'). Walking, the canvas holds the focus (`aria-describedby` the hint, whose second line says how to walk with TalkBack: tested), the arrows are the controls' (they `preventDefault`, so the WebView's spatial navigation leaves them), and Enter (the remote's OK) is `controls.useMiddle()`; `menu()` moves the focus into the card (`toCard`, to the control last left, else the first stop that isn't a text box: the doors toggle), where up and down step through `focusStops` (a radio group one stop), left and right through a choice (clicking each), Enter ticks, and Escape or `back()` walk again (`walk`). A text box stepped onto (the name, the Join form's room) has `inputmode="none"` (common 0.6.1), so the TV's keyboard, which would take the arrows, stays down until OK on it; the next Enter is the box's own: the name kept (`overlay.js` blurs it), the room joined (the form's submit). `remote.answerApp(tv)` puts `window.hallwayTV = { menu, back }` there for the app, which calls them on each press and goes back a page (or leaves) unless one returns true: the contract HallwayApp's `MainActivity` keeps. The hallway gives the `Remote` no `step`: walking, Back is the app's. Its own `tv.js` is only `roomFromInput` (the Join form; it needs the layer's `isRoom`), pure; `test/tv.test.js` has it, the controls' keys, the focus ring and the hint, and common's tests the rest. With TalkBack on, the remote's arrows can't walk, and neither the page nor the app can change that: TalkBack 14 on a TV takes the D-pad's arrows before any app's window (its `TelevisionNavigationController`, which lets them by only while an on-screen keyboard is up) and moves its own focus with them, in the page's order. Checked on the TV with a virtual remote (`/system/bin/hid`; `adb shell input keyevent` goes round TalkBack): Menu reached `MainActivity.dispatchKeyEvent`, the arrows never did, with `role="application"` on the canvas or without. What does reach the page with TalkBack on: OK on the canvas (TalkBack passes OK on for a web element it can't click, so `useMiddle()` still works; on a card control OK is TalkBack's click), Menu and Back (the app's), the remote's channel and media keys, of which `keyOf` reads `ChannelUp` and `ChannelDown` as the up and down arrows and `MediaRewind` and `MediaFastForward` as left and right, so they walk and turn (checked on the TV, the app staying in front), and a gamepad, whose sticks walk and turn.
- `common/gamepad.js` (AriaMoKr/common): pure and allocation-free. A gamepad as a first-person controller, read alike by the sites so a pad feels the same on both sides of a door: `readPad` (dead zone 0.18, linear; A uses, B and Back are both "back", the left stick clicked in hurries; an analogue button counts past half way), `firstPad` (the standard mapping first).
- `overlay.js`: the page around the view, in a `<main>` (index.html) with the canvas (`role="img"`, named in main.js): the doors list (a `<nav>`, each door a link, its name in `color.js`'s `readable` tint of its glow: 4.5:1 on the list plain and hovered, the backgrounds tested against style.css), the Together section, and Settings (a `<details>`): the control panel's Move, Turn and Motion as radio groups, the vignette and seated as checkboxes, and Start / Leave shared session, which press the panel's buttons or set the settings (`onNav`, `onAccess`, `onSession`; `setPanel` from main.js's `showPanel`). The panel is only in 3D, so whatever it offers belongs in Settings too. On a short screen the card scrolls, kept inside it and above the buttons at its foot (`--buttons`, their height, which a `ResizeObserver` sets: two rows on a phone in a session); nothing takes away the focus ring (`:focus-visible`, 2 px: tested), which forced colours keep. With `tv` (the TV app's page) the Together section shows the invite link to type elsewhere (`inviteText`, no Copy pill) and Settings has a Join form (`onJoin`, main.js's `roomFromInput`), hidden in a session.
- `controls.js`: the hall's subclass of common's `Controls` (`common/controls.js`, whose README, "controls.js", says what each device does and what a site gives it, and whose tests cover it). Common's is the walking: desktop, touch, gamepad, TV and XR input into one rig (yaw) + camera (head). The gamepad, as in vrlbry, takes over when used (`padActive`, `onPadActive`: its hint, and the middle of the view is what it points at) and a mouse move or press hands back; `aimMiddle` (a TV's) points at the middle of the view without one, and `useMiddle()` is A or OK; a key is `KEYS[keyOf(e)]` (common/tv.js: `e.code || e.key`, the remote's channel and media keys as the arrows, for TalkBack; `controls.js` passes `KEYS` on for `test/tv.test.js`), and it is the page's when a page control has used it (`defaultPrevented`), in a form control or a `data-own-keys` element, and for Space or Enter on a button or a link; two fingers neither look nor tap; `walkTo(x, z, { face, then })`, and with `reduceMotion` every walk jumps; in VR the left stick walks or aims a teleport (`move`), the right one snaps or turns smoothly (`turn`), and teleports go through `onTeleport` (main.js blinks the view). What a click, a tap, A, OK or a trigger is on goes to `use(hit, how)`: common's takes the doorway (`onDoor(how, hit)`) and `walkable` ground (a walk there on a screen, a teleport in VR), and the reticle is light only there and on what can be used. The hall's own: `layout` (set after `super()`); `castRay` and `clampWalk` (layout.js's `castRay` and `clampToHall`), and its hit's `door`, `u` and `v` (the `hit` option); its doors: `usable` is `'door'` only on a door that leads somewhere (the cursor, the dot, the reticle), but common's `use` passes every doorway on, so `onDoor` still says a closed one isn't open yet; `pointedDoor`, the open door pointed at (`_setHover`), which `hall.update` lights and the overlay names (`?.env`), as common's `hoverDoor` is only whether it is a doorway; `walkInto(door)`, up to it and through it, facing it from the first step (`false`, `_startWalk`'s `turn`: `go()` hands the view on as the head crosses the threshold, 0.8 m into the last leg, so a walk that looked where it went would turn the next site's view by up to 43°); and the control panel's `hoverPanel`, `onPanel` and `_press`. `main.js`: renderer, loop, going through doors (`go`: a fade, `common/fade.js`'s `Fade`, then `location.assign` of the door's link), arrival, VR entry including `sessiongranted`, fullscreen (the overlay's button, with webkit fallbacks; Esc, or a gamepad's B or Back, leaves it).
- Accessibility (`main.js`, from `common/access.js`; localStorage `hallway.access`, shared by every site on the origin, read again on a `storage` event and on `pageshow`, as the movement choice is): `reduce` (`reduceMotion`: the setting, or the system's `prefers-reduced-motion`, watched) makes a walk jump (common's, by `controls.reduceMotion`), a door clicked on a screen gone through at once, every fade but the teleport's a 0.08 s blink (`fadeTime`), holds the doorways' `uTime` (the loop's `time` stops), skips the wave's bob (`together.reduceMotion`) and puts `reduce-motion` on `<html>` (no CSS transitions); a `Vignette` on the camera beside the `Fade`, fed each frame the controls' `moveSpeed` and `turnRate` (the sticks' smooth walking and turning in VR, 0 for snap turns and teleports), hidden from the door views and the link preview as the fade is; seated lifts the rig by `eyeLift` in VR only (`controls.setEyeLift`, kept by `setPose` and on entering VR, 0 on leaving it).

## Conventions

- Client URLs stay relative: the site may live under a path (`/hallway/`). Tested.
- Types, with no build: `tsconfig.json` checks `public/js/` from its JSDoc, as the template's does (`allowJs`, `checkJs`, `noEmit`; `moduleResolution` `bundler`: three's types from `@types/three`, common's and the layer's from their `.d.ts`; `lib` ES2022, DOM and DOM.Iterable; `types: []`). The page is served unchanged and the import map stays. `test/types.test.js` runs tsc, so `npm test` and the Pages workflow do, and fails rather than skips without TypeScript (devDependencies: `typescript` 5.9.3, `@types/three` 0.186.0). What TypeScript's DOM library leaves out (WebKit's fullscreen names, `window.hallwayXrGranted`, `window.__hallway`) is in `types/globals.d.ts`, never served. Not `strict` yet: with it tsc finds 560, nearly all parameters with no type and values that may be null, which come a file at a time, as in the template; `tools/` and `test/` wait too.
- Quest 3 is the performance target. Keep draw calls few (one mesh per material: merge static geometry into a `Builder`), allocate nothing per frame (reuse vectors and hit objects, index loops over `session.inputSources`), and keep lighting baked.
- Coordinates: metres, floor y = 0, entrance wall z = 0, hall along -z, left is -x; yaw 0 faces -z.
- Scripted testing: `window.__hallway` (renderer, scene, camera, rig, hall, layout, controls, overlay, fade, `go`, `enterVR`, `together`, `vignette`, `access` (the settings and `reduce`), `doorViews()`, `hallView()`, `tick(dt, n)`, `xrDevice`, `remote` (in TV mode)). The settings: `controls.onPanel('motion:reduce')` (and `vignette:on`, `seated:on`, …) presses the panel's buttons. A shared session needs two pages: open the same `?room=` in two tabs (each tab is its own visitor), `controls.onPanel('session')` presses Start / Leave, `overlay.myName` (set its value, dispatch `change`) renames, `overlay.wave.click()` waves (IWER: `xrDevice.controllers.right.updateButtonValue('squeeze', 1)`), and layersharedsession's test page in the same room lists everyone and logs who came, went, renamed and waved. Offline: define `navigator.onLine` as false and dispatch `offline`. A hidden browser pane gets no animation frames, so drive it with `tick()`. `?xr=emulate` installs IWER; aim its controllers with `xrDevice.controllers.right.position/quaternion`, `updateButtonValue('trigger', 1)`, `updateAxes('thumbstick', x, y)`. A gamepad: replace `navigator.getGamepads` with one returning a fake `{ connected: true, axes, buttons: [{ pressed }] }` and dispatch a `gamepadconnected` event. TV mode: `?tv=emulate`, then `remote.menu()` (or `hallwayTV.menu()`) and keydown events (`ArrowDown`, `Enter`, `Escape`) on `document.activeElement` (a synthetic Enter opens no `<details>` and submits no form: for those, real key presses, the browser pane's `computer` keys); on the TV itself, see HallwayApp's README (its debug build's `url` extra, `adb reverse`, WebView DevTools). The browser pane never grants fullscreen: define `document.fullscreenElement` and dispatch `fullscreenchange` (real fullscreen was checked in Quest Browser, pressing the button over DevTools with `userGesture`).
- The embedded browser pane serves the dev server on port 8088 (`.claude/launch.json`). `hallway-quest` serves it on `127.0.0.1:8089` as well, for the tools that reach it from a Quest through `adb reverse` (`--port 8089`): Quest Browser cannot reach the IPv6-only one there (checked).
